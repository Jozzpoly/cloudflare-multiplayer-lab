# Gate 4 — Authoritative Shared Simulation Lab

## Gate 4A — Fixed simulation substrate

**Status:** IMPLEMENTED / AWAITING REPOSITORY CI + CLOUD RUNTIME EVIDENCE  
**Branch:** `gate-4-shared-simulation-lab`

## Canonical Gate 4 question

Can one Cloudflare Durable Object act as a useful server for a small continuous physically shared world for roughly 1–5 mobile players, with measurable prediction/reconciliation, bounded network stress and an acceptable personal-session cost model?

Gate 4 is a program with internal checkpoints. Gate 4A does **not** answer the whole question. It establishes the measurement/simulation substrate on which later shared-physics falsifiers can be trusted.

## Gate 4A question

Can the existing Neon Salvage world be moved from input-driven integration to a real fixed-step authoritative server simulation without hiding timing failures, while remaining mobile-playable and reproducible enough for later A/B experiments?

## Fixed contract

The baseline deliberately separates three cadences:

- authoritative simulation: **20 Hz** / 50 ms fixed step,
- authoritative snapshot broadcast: **10 Hz**,
- client input transport: **~15 Hz** baseline heartbeat.

These are separate architectural variables. Receiving an input message must not advance world time. Input only updates the latest control state and sequence number. World state advances only inside the simulation loop.

## Scheduler behavior

The active Durable Object uses a fixed-step accumulator with bounded catch-up:

- at most 4 simulation steps may be executed in one pump,
- excess backlog is counted as dropped ticks instead of entering a spiral-of-death,
- callback drift and tick execution cost are sampled and exposed,
- the timer starts when the first player joins,
- the timer is cleared after the last player leaves so the object can return to an idle/hibernatable lifecycle.

Gate 4A intentionally accepts that an active fixed-tick session is non-hibernating by design.

## Input lease

The server treats control input as a lease. If no fresh input arrives for 600 ms, movement input becomes neutral and a queued dash is cleared. This is specifically meant to prevent a backgrounded/throttled mobile browser from leaving a vehicle/player in a permanent runaway state.

## Deterministic run/reset

A run has an explicit 32-bit seed and run id.

- pickup placement is generated by a deterministic PRNG,
- player spawn is derived from `seed + playerId`,
- the LAB panel can reset the shared run to a supplied seed,
- reset clears motion, scores, combos, input state and scheduler counters for active players.

This is a research control, not a public-game permission model. Any connected lab client may reset the shared run.

## Measurement contract

Server telemetry exposed in snapshots:

- target simulation and snapshot frequencies,
- active players,
- simulation tick and snapshot sequence,
- tick execution p50/p95,
- scheduler drift p50/p95,
- dropped ticks,
- catch-up steps,
- inputs/sec,
- snapshots/sec,
- approximate inbound/outbound application bytes/sec,
- active-run duration.

Client telemetry:

- RTT p50/p95,
- approximate snapshot age using ping-derived server clock offset,
- snapshot inter-arrival p95,
- local prediction correction p50/p95,
- rendered FPS,
- client input messages/sec,
- approximate client application bytes/sec.

These are falsification measurements, not final production SLOs.

## Preserved control specimen

Gate 4A intentionally keeps the Gate 3 Neon Salvage gameplay recognizable:

- same mobile joystick/dash interaction,
- same shared pickups/scoring,
- same one-world multiplayer model.

The point is to change the timing/authority substrate without simultaneously adding Reactor Core, vehicle dynamics, debris or new game rules. A visible behavioral regression is therefore easier to attribute.

## Gate 4A success criteria

1. GitHub CI and Wrangler dry-run pass on the real repository toolchain.
2. Cloudflare deploy succeeds with the existing `WORLD` Durable Object binding.
3. A real mobile client remains playable after the authority model changes.
4. World motion continues under fixed simulation cadence and is not advanced directly by input callbacks.
5. Server telemetry reports near-target simulation/snapshot cadence without sustained dropped-tick growth in a normal 1–2 client session.
6. Prediction correction metrics remain bounded enough that normal play does not become dominated by visible snapping.
7. Background/throttled input eventually neutralizes through the server lease.
8. Resetting the same seed reproduces initial pickup layout and deterministic player spawn for the same callsign.

## Gate 4A non-claims

This stage does not establish:

- shared rigid-body physics,
- player-player or player-object physical interaction,
- vehicle dynamics,
- 3–5 real-device pressure behavior,
- bad-network robustness,
- 20 Hz as the final best cadence,
- low cost at scale,
- suitability as a full vehicle-physics server.

## Natural next boundary

Only after Gate 4A runtime evidence is coherent should Gate 4B introduce the first genuinely shared dynamic body (Reactor Core / debris) and physical impulse interaction. If the fixed simulation substrate is already unstable, gameplay expansion must stop and the substrate must be falsified or corrected first.

## Known hardening debt

The repository still has no committed package lock. Exact direct tool versions remain pinned, but dependency locking must be normalized before this lab is treated as a reusable production template.
